### 5.1 VRRP (RFC 9568)

**Cambio de nombres.** La 9568 §1.1 («Differences from RFC 5798») actualiza la terminología a lenguaje inclusivo: el router que reenvía pasa a
llamarse **«Active Router»** (en la 5798, «Master»); `Master_Down_Interval` y `Master_Adver_Interval` pasan a
**`Active_Down_Interval`** y **`Active_Adver_Interval`**.

| Apartado | Qué fija | Cifras literales |
|---|---|---|
| §5.1.1.3 / §5.1.2.3 | TTL / Hop Limit | **255**; se descarta lo que llegue con otro valor |
| §5.1.1.2 / §5.1.2.2 | Destino multidifusión | IPv4 **224.0.0.18**; IPv6 **ff02:0:0:0:0:0:0:12** |
| §5.1.1.4 / §5.1.2.4 | Protocolo IP | **112** |
| §5.2.4 y §6.1 | Prioridad | **255** = el dueño de la dirección IPvX virtual; **1–254** para los de respaldo, por defecto **100**; **0** = el Active Router deja de participar (los de respaldo toman el relevo sin esperar `Active_Down_Interval`) |
| §6.1 | VRID | **1–255**, sin valor por defecto |
| §5.2.7 y §6.1 | `Advertisement_Interval` | En **centisegundos**; por defecto **100 cs (1 s)**; campo de 12 bits |
| §6.1 | `Skew_Time` | `((256 - Priority) * Active_Adver_Interval) / 256` |
| §6.1 | `Active_Down_Interval` | `(3 * Active_Adver_Interval) + Skew_Time` |
| §6.1 | `Preempt_Mode` | Por defecto **True**; el dueño de la dirección (prioridad 255) **siempre** se impone, tenga lo que tenga esa opción |
| §6.1 | `Accept_Mode` | Por defecto **False** (el Active Router que no es el dueño no acepta paquetes dirigidos a la dirección virtual, salvo NS/NA de IPv6) |
| §7.3 | MAC virtual | IPv4 **00-00-5E-00-01-{VRID}**; IPv6 **00-00-5E-00-02-{VRID}** (hasta 255 routers virtuales por LAN) |
| §3 | Convergencia | Elección del nuevo Active Router en **< 4 s** con el intervalo por defecto, configurable a **< 1/25 s** |
| §1.4 | Frente a ND de IPv6 | Con VRRP el cambio de router por defecto lleva unos **tres segundos** con valores por defecto |

**Aritmética (calculada aquí con las fórmulas de §6.1, `Active_Adver_Interval` = 100 cs):**

| Prioridad del de respaldo | `Skew_Time` | `Active_Down_Interval` |
|---|---|---|
| 100 (por defecto) | (156 × 100) / 256 = **60,9375 cs** ≈ 0,61 s | 300 + 60,94 = **360,94 cs ≈ 3,61 s** |
| 200 | (56 × 100) / 256 = 21,875 cs | 321,875 cs ≈ 3,22 s |
| 254 | (2 × 100) / 256 = 0,78125 cs | 300,78 cs ≈ 3,01 s |

Cuanto mayor la prioridad, menor el sesgo: el de respaldo con más prioridad declara caído al activo antes.

| 1794 §2 | Historia: el «Round Robin» de BIND ordenaba los registros A por turnos **sin mirar la carga**; criterios del grupo de trabajo (compatibilidad, datos frecuentes, varias direcciones para recuperarse si una cae dentro del TTL…) | — |

## 9. HAProxy (valor del fabricante)

Fuente: **HAProxy 3.4 (LTS)**, «Configuration Manual», `https://docs.haproxy.org/3.4/configuration.html`, y
«Management Guide», `https://docs.haproxy.org/3.4/management.html`. Versiones según
`https://www.haproxy.org/` (2026-11-27): 3.4 LTS (publicada 2026-06-03, fin 2031-Q2), 3.2 LTS (fin 2030-Q2),
3.0 LTS (fin 2029-Q2). Se comparó una frase con los manuales 3.2 y 3.0 (ver «algoritmo por defecto»).

### 9.1 Algoritmos (`balance`)

| Algoritmo | Qué hace (paráfrasis) | Notas del fabricante |
|---|---|---|
| `roundrobin` | Cada servidor por turno, según su peso; dinámico (los pesos cambian en caliente) | Límite de diseño: **4095** servidores activos por *backend* |
| `static-rr` | Igual, pero estático: cambiar el peso en caliente no surte efecto; sin límite de servidores | — |
| `leastconn` | Al servidor con **menos conexiones**; *round robin* entre empatados; cuenta también la cola | Recomendado para sesiones largas (LDAP, SQL, TSE); poco adecuado para HTTP de sesiones cortas |
| `first` | Al primer servidor (por identificador) con hueco; al llegar a su `maxconn`, al siguiente | Sirve para usar el mínimo de servidores; sin `maxconn` no tiene sentido; ignora pesos |
| `source` | Hash de la **IP de origen** dividido por el peso total: misma IP, mismo servidor **mientras no cambie el número de servidores**; si cambia, muchos clientes se mueven | Para modo TCP sin *cookies*, o persistencia «best-effort» |
| `uri` | Hash de la parte izquierda del URI (o del URI entero) | Para cachés; solo en *backend* HTTP |
| `url_param` | Hash de un parámetro de la URL (o del cuerpo de un POST con `check_post`) | Si no aparece, *round robin* |
| `hdr(<name>)` | Hash de una cabecera HTTP (p. ej. `Host`, con `use_domain_only`) | Si falta, *round robin* |
| `hash` | Hash de una expresión de muestreo cualquiera | — |
| `random` / `random(<draws>)` | Número aleatorio como clave de un hash consistente; con `<draws>`, elige el menos cargado de N sorteos | **Por defecto 2** («Power of Two Random Choices») |
| `rdp-cookie` | Hash de la *cookie* RDP (`mstshash`) | Persistencia degradada para RDP |

**Algoritmo por defecto:** en **3.4** «set to "random" when no other algorithm, mode nor option have been set»; en
**3.2 y 3.0** la misma frase dice **roundrobin**. Los algoritmos de hash son estáticos por defecto (cambiable con
`hash-type`).

| Parámetro de `server` | Valor del fabricante |
|---|---|
| `weight` | Por defecto **1**, máximo **256**; **0** = no recibe reparto pero sí conexiones persistentes |
| `maxconn` | Por defecto **0** (ilimitado); por encima, a la cola. En modo HTTP limita peticiones concurrentes |
| `backup` | Solo se usa si no queda ningún servidor normal; por defecto solo el **primer** *backup* operativo (salvo `allbackups`) |
| `slowstart` | Tras volver de un fallo, peso y `maxconn` suben linealmente de 0 a 100 % en ese tiempo; no se aplica al arrancar HAProxy |

### 9.2 Comprobaciones de salud

| Parámetro | Valor del fabricante |
|---|---|
| `check` | Activa las comprobaciones; sin él el servidor se da **siempre por disponible**. Sin otro método, «disponible» = se puede **establecer la conexión** (TCP, o TLS con `check-ssl`) |
| `inter` | Intervalo entre comprobaciones; por defecto **2000 ms**. También hace de *timeout* si no hay `timeout check` |
| `fastinter` | Intervalo mientras el servidor está en transición (bajando o subiendo); si no se fija, `inter` |
| `downinter` | Intervalo con el servidor caído del todo; si no se fija, `inter` |
| `fall` | Caído tras **3** comprobaciones fallidas seguidas (por defecto) |
| `rise` | Operativo tras **2** comprobaciones correctas seguidas (por defecto) |
| `option httpchk` | Tras conectar envía una petición HTTP completa; valen **2xx y 3xx**, todo lo demás (o no responder) es fallo. Por defecto método **OPTIONS**, URI **/**, versión **HTTP/1.0**, sin `Host` |
| `http-check expect` | Comprueba la respuesta por `status`, `rstatus`, `hdr`, `fhdr`, `string` o `rstring` (negable con `!`) |
| `http-check disable-on-404` | Un **404** saca al servidor del reparto pero sigue atendiendo las conexiones persistentes (estado «NOLB»): apagado ordenado |
| `observe layer4 \| layer7` | **Comprobación pasiva** (observa el tráfico real); desactivada por defecto y exige `check`. En `layer7` valen los códigos 100–499, 501 y 505 |
| `error-limit` | Errores seguidos que disparan `on-error`; por defecto **10** |
| `on-error` | `fastinter`, **`fail-check`** (por defecto), `sudden-death`, `mark-down` |

**Estados administrativos** (Management Guide, `set server <backend>/<server> state [ ready | drain | maint ]`):
**ready** = normal; **drain** = fuera del reparto, pero se sigue comprobando y acepta **nuevas conexiones
persistentes**; **maint** = sin tráfico **ni comprobaciones**.

**Sin servidores:** el manual (§1.4.1 «The response line») dice que HAProxy devuelve **503** «when no server was
available to handle the request»; **502** si el servidor da una respuesta vacía, no válida o incompleta; **504** si
salta el *timeout* de respuesta.

### 9.3 Persistencia, modos y cabeceras

| Elemento | Valor del fabricante |
|---|---|
| `cookie <name> insert` | HAProxy **inserta** la *cookie* de persistencia si el cliente no la trae; es «session cookie» (no se guarda en disco); conviene `nocache` o `postonly` si hay cachés |
| `cookie <name> rewrite` | La *cookie* la crea la aplicación y HAProxy **reescribe su valor** con el identificador del servidor; no recomendado para despliegues nuevos |
| `cookie <name> prefix` | HAProxy **antepone** el identificador del servidor a una *cookie* existente de la aplicación y lo quita en las peticiones |
| Opciones de `cookie` | `indirect`, `nocache`, `postonly`, `preserve`, `httponly`, `secure`, `domain`, `maxidle`, `maxlife`; el valor por servidor lo da `server ... cookie <value>` |
| `stick-table` | Tabla de persistencia; `type` y `size` obligatorios; `expire` (máximo algo más de 24 días; sin él, las entradas no caducan solas); `peers` sincroniza la tabla entre instancias |
| `stick on <pattern>` | Asocia un patrón de la petición (p. ej. `src`) a un servidor |
| Persistencia por **ID de sesión SSL** (ejemplo del manual) | En `mode tcp`, aprende el ID de sesión del ClientHello y del ServerHello con `req.payload_lv(43,1)` y una `stick-table type binary len 32` |
| `mode tcp` | TCP puro, sin examen de capa 7; **es el modo por defecto**; para SSL, SSH, SMTP… |
| `mode http` | Analiza la petición antes de conectar; rechaza lo que no cumple la RFC; permite filtrar y conmutar por contenido |
| `req.ssl_sni` | Lee el SNI del ClientHello **sin descifrar** (en modo TCP); ejemplo del manual: `use-server www if { req.ssl_sni -i www.example.com }` |
| `option forwardfor` | Añade **X-Forwarded-For** con la IP del cliente; el servidor debe usar **la última** aparición (el cliente puede traer una falsa); `if-none` solo en entornos de confianza |
| `option forwarded` | Añade la cabecera **`Forwarded` de la RFC 7239** (`proto`, `host`, `by`, `for`…) |
| `send-proxy` / `send-proxy-v2` | Envía la cabecera del **protocolo PROXY** (v1 / v2) en cada conexión al servidor; no usar si el servidor no lo entiende; v2 puede llevar ALPN |
| `abortonclose` | Por defecto en conexiones TLS entrantes; el manual pone como ejemplo una conmutación VRRP entre dos HAProxy en la que todos los clientes reconectan a la vez y hacen saludos TLS completos |

## 13. Microsoft: clúster, quórum y *floating IP* (valor del fabricante)

### 13.1 Clúster de conmutación por error

Fuente: «Failover clustering overview», `https://learn.microsoft.com/en-us/windows-server/failover-clustering/failover-clustering-overview`.

| Concepto | Qué dice (paráfrasis) |
|---|---|
| Latido | La salud del clúster se vigila con señales de **latido** («heartbeat»), a menudo por una red privada dedicada; si hay un problema, se inicia la **conmutación** («failover») automática |
| Activo-activo | Todos los nodos trabajan a la vez y se reparten la carga; aprovecha mejor los recursos |
| Activo-pasivo | Unos nodos activos y otros en espera para relevar; desaprovecha hardware pero es más simple y predecible |
| Quórum | Mínimo de votos para que el clúster funcione; evita el ***split-brain*** (partes del clúster que intentan funcionar por separado). Modelos: Node Majority, Node and Disk Majority, Node and File Share Majority, No Majority (Disk Only) |

### 13.2 Quórum y testigo

Fuente: «Understand cluster and pool quorum», `https://learn.microsoft.com/en-us/windows-server/storage/storage-spaces/quorum`.

| Concepto | Qué dice (paráfrasis) |
|---|---|
| Quórum | El clúster suele necesitar **más de la mitad** de los nodos en marcha; así, tras una partición de red solo **un** grupo sigue en línea y no escriben dos a la vez en el mismo disco (*split-brain*) |
| Número par | La mayoría funciona limpia con número **impar** de votos; con número par y sin testigo, se anula el voto de un nodo |
| Testigo | Con dos nodos y testigo: 3 votos; si cae uno, el superviviente tiene **2/3** y sigue. Sin testigo, con dos nodos, si cae el que vota el clúster cae: por eso Microsoft recomienda **configurar siempre un testigo** |
| Quórum dinámico | Tras cada caída la mayoría se recalcula entre los supervivientes («last-man standing») |

Página de despliegue de testigos (se pidió `.../failover-clustering/manage-cluster-quorum`, que **redirige** a
`https://learn.microsoft.com/en-us/windows-server/failover-clustering/deploy-quorum-witness`, título «Deploy a quorum witness»): tres tipos, **cloud witness** (Azure Storage, puerto **443**), **disk witness**
(disco compartido) y **file share witness** (SMB 2 o superior, ≥ **5 MB** libres; DFS no admitido).

### 13.3 Azure Load Balancer: *floating IP*

Fuente: «Azure Load Balancer Floating IP configuration», `https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-floating-ip`.
Con *floating IP* activada, Azure entrega el tráfico con la **IP del *frontend*** del balanceador como destino (sin
ella, con la IP de la máquina); el sistema invitado debe tener esa IP en una interfaz *loopback* y aceptar
paquetes en interfaces que no tienen la dirección (modelo «weak host» en Windows). La página **no** usa el término
DSR ni describe el camino de vuelta: `⚠ sin fuente` para «DSR».

## 14. Disponibilidad: fórmulas y tabla de «nueves»

Fuente de las fórmulas: **AWS Well-Architected Framework, Reliability Pillar, «Availability»**,
`https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/availability.html` (**valor del
fabricante** como fuente; las fórmulas son aritmética general). **No se buscó** una norma (IEC/ISO/NIST) con la
fórmula; solo se consultó AWS: `⚠ sin fuente` normativa.

| Concepto | Qué dice la página | Literal |
|---|---|---|
| Definición | Disponibilidad = porcentaje de tiempo en servicio en un periodo (normalmente un mes o un año); «five nines» = 99,999 %. AWS desaconseja excluir el mantenimiento programado del tiempo total | — |
| Estimación con MTBF y MTTR | Disponibilidad estimada = **MTBF / (MTBF + MTTR)** (MTBF = «Mean Time Between Failure», MTTR = «Mean Time to Recover» en esa página). **La fórmula solo figura como imagen**; su texto alternativo es «Avail_EST = MTBF / (MTBF + MTTR)» | Ejemplo: MTBF **150 días**, MTTR **1 h** → **99,97 %** |
| Dependencias duras (en serie) | La disponibilidad es el **producto** de las disponibilidades | 99,99 % × 99,99 % × 99,99 % = **99,97 %** |
| Componentes redundantes (en paralelo) | **100 % menos el producto de las indisponibilidades** | 100 % − (0,1 % × 0,1 %) = **99,9999 %**; atajo: si todo son nueves, se suman los nueves (3 + 3 = 6) |
| Tabla de AWS (anual, redondeada) | 99 % → 3 días 15 h; 99,9 % → 8 h 45 min; 99,95 % → 4 h 22 min; 99,99 % → 52 min; 99,999 % → 5 min | — |

**Comprobación del ejemplo (calculada):** 150 días = 3600 h → 3600 / 3601 = 0,999722 → **99,97 %**.
Serie de tres a 99,99 %: 0,9999³ = 0,99970003 → **99,97 %**. Paralelo de dos a 99,9 %: 1 − 0,001² = 0,999999.

|---|---|---|---|
| 99 % | 0,01 | 5256 min = **87 h 36 min** (3 d 15 h 36 min) | 432 min = **7 h 12 min** |

## 17. Discrepancias y trampas

1. **TLS 1.3 ya no es la 8446.** La **RFC 9846** (jul. 2026) obsoleta la 8446 (y la 5246, 5077, 7627, 8422…).
   Citar la 9846. Ojo con la numeración: CertificateRequest es §4.4.2 en la 9846 (§4.3.2 en la 8446);
   NewSessionTicket, §4.7.1 (antes §4.6.1). La 5246 (TLS 1.2) figura como obsoleta por **8446 y 9846**.
2. **ECH ya es RFC**: **9849** (PROPOSED STANDARD, mar. 2026), no un borrador. Con ECH el cliente **SHOULD** poner el
   `public_name` en el SNI exterior (9849 §6.1). Deducción (no lo dice la RFC con estas palabras): un equipo que
   enrute por SNI sin descifrar ya no ve el nombre real, salvo que sea el propio «client-facing server».
3. **Reanudación por «session ID» ya no existe en TLS 1.3** (9846 §2.2: «session IDs» y «session tickets» de
   TLS 1.2 están obsoletos; se usa PSK). La persistencia por ID de sesión SSL del ejemplo de HAProxy
   (`req.payload_lv(43,1)`) depende de esos campos de TLS 1.2: **no** venderla como método actual sin matizar.
4. **Cookies: la RFC sigue siendo la 6265.** El 6265bis (draft -22) está en «RFC Ed Queue» pero **sin número**;
   `SameSite` no está en la 6265.
5. **VRRP: 5798 → 9568, y «Master» → «Active».** `Master_Down_Interval` ahora es **`Active_Down_Interval`**.
   Los apuntes antiguos (y `op1m4`, si usó la 5798) dicen «Master»: en preguntas nuevas, usar la 9568 o dar los
   dos nombres. Los valores no cambian (comprobado en la 5798): prioridad 255/1–254 (100 por defecto)/0, 100 cs, MAC
   00-00-5E-00-01-{VRID}, `Preempt_Mode` True.
6. **HSRP no es estándar IETF.** La 2281 es INFORMATIONAL, describe un protocolo de Cisco y lleva nota de
   patente. Cisco HSRP: 1985/UDP, 224.0.0.2, hello 3 s, hold 10 s, MAC 00-00-0C-07-AC-XX. VRRP: protocolo IP 112,
   224.0.0.18, 1 s. No cruzar cifras.
7. **El algoritmo por defecto de HAProxy depende de la versión.** 3.4 LTS: **random** (con 2 sorteos); 3.2 y 3.0
   LTS: **roundrobin**. NGINX y AWS ALB: **round robin** (ponderado en NGINX). Preguntar siempre «según la
   documentación de X versión Y», nunca «el algoritmo por defecto de un balanceador».
8. **Valores de las comprobaciones de salud: cada fabricante, los suyos.**

   | | Intervalo | Para caer | Para volver | Qué vale |
   |---|---|---|---|---|
   | HAProxy (`check`) | 2 s (`inter`) | 3 (`fall`) | 2 (`rise`) | TCP: conectar; `httpchk`: 2xx–3xx |
   | NGINX Plus (`health_check`) | 5 s | 1 (`fails`) | 1 (`passes`) | 2xx–3xx |
   | NGINX libre (pasiva) | — | 1 fallo en 10 s (`max_fails`/`fail_timeout`) | tras 10 s, prueba con tráfico real | lo que diga `proxy_next_upstream` |
   | AWS ALB | 30 s | 2 | 5 | 200 |
   | AWS NLB | 30 s | 2 | 5 | TCP; HTTP 200–399 |

9. **NGINX libre no tiene comprobaciones activas.** `health_check` es de NGINX Plus; la versión libre solo hace
   comprobaciones **pasivas**. La guía dice que `max_fails` cuenta fallos «consecutive»; la página del módulo
   habla de fallos «in the duration set by» `fail_timeout`: no preguntar por esa diferencia.
10. **`sticky` en NGINX**: hasta la 1.29.6 era solo de NGINX Plus; hoy está en la versión libre (salvo `sync`).
    Material antiguo dirá «solo Plus». `proxy_protocol v2` en `stream` llegó en la **1.31.4**.
11. **`ip_hash` de NGINX usa los tres primeros octetos** de la IPv4: todos los clientes de una misma /24 van al
    mismo servidor. HAProxy `source` usa la IP entera. Con NAT masivo (muchos usuarios tras una IP), ambos
    concentran carga.
12. **«Sticky session» tiene muchos nombres**: persistencia (HAProxy «persistence», `stick-table`), «session
    affinity» (NGINX, AWS), «stickiness» (AWS). Y la *cookie* tiene nombres de producto: el que se configure
    en HAProxy (`cookie <name>`), `srv_id` en el ejemplo de NGINX, **`AWSALB`/`AWSALBCORS`** en AWS
    (fijos). La *cookie* insertada por HAProxy es de sesión; la de AWS caduca a los 7 días (no configurable).
13. **`X-Forwarded-For` no está normalizada**; la estándar es **`Forwarded`** (RFC 7239). HAProxy tiene las dos
    (`option forwardfor` y `option forwarded`); NGINX, la variable `$proxy_add_x_forwarded_for`; AWS ALB, XFF en
    modo `append`. Y ninguna es fiable si viene del cliente (7239 §8.1; HAProxy: usar la **última** aparición).
14. **El protocolo PROXY no es una RFC.** Es una especificación de HAProxy Technologies (v1 texto, v2 binario),
    adoptada por NGINX y AWS NLB. Rotularlo siempre así.
15. **503 frente a 502 y 504.** 503: no hay servidor disponible (HAProxy) o el servidor está sobrecargado o en
    mantenimiento (9110). 502: respuesta no válida del servidor de dentro. 504: no respondió a tiempo.
16. **Cuando todos los miembros caen**: HAProxy devuelve **503**; AWS ALB hace lo contrario, **«fail open»**, y
    reparte entre todos aunque estén mal. No generalizar.
17. **Drenaje no es mantenimiento.** HAProxy `drain`: fuera del reparto, pero sigue comprobándose y acepta nuevas
    conexiones **persistentes**; `maint`: sin tráfico ni comprobaciones. NGINX `down`: fuera; `backup`: solo si no
    quedan principales. AWS: *deregistration delay* de 300 s por defecto.
18. **Modo por defecto de HAProxy es `tcp`**, no `http`. Sin `mode http` no hay `Host`, rutas ni *cookies*.
19. **ECMP y hash: cuánto se mueve al cambiar un miembro.** Modulo-N: (N−1)/N de los flujos; hash-threshold: 1/4–1/2;
    HRW: 1/N (2991 §4). Lo mismo avisan HAProxy (`source`: «many clients will be directed to a different server») y
    NGINX (`hash` sin `consistent`: «remapping most of the keys»).
20. **El servidor ve la IP del balanceador, salvo que…**: LSNAT (solo destino) le deja ver la IP real del cliente pero
    exige que la vuelta pase por el balanceador; LS-NAPT (origen y destino) no lo exige pero el servidor ve al
    balanceador (2391). AWS NLB preserva la IP según el tipo de destino; si no, PROXY v2.
21. **Anycast y TCP.** Funciona bien para transacciones cortas (DNS/UDP); con TCP, un cambio de ruta o ECMP puede
    partir una conexión entre nodos (4786 §4.1 y §4.4.3).
22. **BFD no es una comprobación de salud de aplicación.** Detecta fallos del **camino de reenvío** entre equipos
    adyacentes (5880 §1), no si la web responde.
23. **MTTR tiene varias lecturas.** AWS lo expande como «Mean Time to Recover»; otras fuentes dicen «repair» o
    «restore»: `⚠ sin fuente` normativa. En preguntas, definirlo en el enunciado.
24. **La fórmula MTBF/(MTBF+MTTR) de AWS está en una imagen** (texto alternativo); citarla como de AWS
    Well-Architected, no como norma.
25. **Redondeo de la tabla de nueves.** AWS da «52 min» y «5 min» al año; la aritmética exacta (365 días) da 52 min
    33,6 s y 5 min 15,4 s. Fijar en cada pregunta si el año es de 365 días y el mes de 30.
26. **Serie frente a paralelo.** En serie (dependencias duras) se **multiplican disponibilidades** y el total baja;
    en paralelo (redundancia independiente) se **multiplican indisponibilidades** y el total sube. La independencia
    es una hipótesis: dos balanceadores en el mismo CPD y la misma línea no son independientes.
27. **SNI no admite direcciones IP** (6066 §3): quien se conecta por IP no puede enviar ese nombre. Qué
    certificado sirve entonces el balanceador depende del producto: `⚠ sin fuente`.
28. **HTTP/2 y reutilización de conexiones.** Con un terminador TLS que elige *backend* por SNI, el navegador puede
    reutilizar una conexión para otro nombre del mismo certificado y acabar en el *backend* equivocado (9113
    §9.1.1); la salida es responder **421**. HAProxy, en su parámetro `sni`, recuerda que en HTTPS el SNI debe
    coincidir con `Host` y que el cliente puede usar varios nombres en la misma conexión: enrutar por `Host`.
29. **«GSLB», «DSR», «N+1», «2N», «failback», «WAF»**: términos de producto o de práctica sin fuente primaria en este
    dossier (ver §18).
